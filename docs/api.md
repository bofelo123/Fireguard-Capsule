# FireGuard Capsule™ API

## API Documentation

**Project:** FireGuard Capsule™
**System:** AI-Powered Wildfire Monitoring, Early Warning and Early-Response System
**Backend:** FastAPI
**Database:** SQLite with SQLAlchemy
**Frontend:** Flutter
**Primary API Base:** `http://127.0.0.1:8000` during local development

---

## 1. Overview

The FireGuard Capsule API provides the backend services that connect the FireGuard mobile/web application, wildfire detection capsules, environmental intelligence, AI analysis, NASA FIRMS fire intelligence, geographic information, authentication, and the database.

The API is designed around a production-style separation of responsibilities:

```text
FireGuard Flutter Application
          │
          │ HTTPS / JSON
          ▼
     FastAPI Backend
          │
          ├── Authentication
          ├── Capsule Management
          ├── Telemetry
          ├── AI Fire Analysis
          ├── Alert Management
          ├── NASA Fire Intelligence
          ├── GIS / Risk Information
          └── FireGuard Assistant
          │
          ▼
      SQLAlchemy
          │
          ▼
      SQLite Database
```

The API also provides the integration boundary for future physical FireGuard Capsule hardware.

The current development environment uses SQLite. The API architecture is designed so that the persistence layer can be migrated to a production database system when deployment requirements demand it.

---

# 2. Design Principles

The FireGuard API follows these principles:

* Real backend services rather than UI-only logic.
* JSON-based API communication.
* Clear separation between frontend and backend responsibilities.
* Database-backed alert persistence.
* Server-side AI analysis.
* Real sensor telemetry support.
* Environmental intelligence integration.
* NASA FIRMS used as supporting fire intelligence.
* Authentication for application and device access.
* No fabrication of sensor measurements.
* No fabrication of environmental measurements.
* Explicit handling of unavailable environmental intelligence.
* Traceable AI evidence associated with generated alerts.
* Hardware integration through defined API boundaries.
* Reproducible local development.

The API is intended to support both current development and future deployment of physical FireGuard Capsules.

# 3. Local Development

Start the backend from the project root:

```powershell
cd C:\FlutterProjects\livesti_guard\fireguard
```

Then enter the backend directory:

```powershell
cd .\fireguard_backend
```

Start the FastAPI development server:

```powershell
uvicorn main:app --reload
```

The local API is normally available at:

```text
http://127.0.0.1:8000
```

FastAPI automatically exposes interactive API documentation at:

```text
http://127.0.0.1:8000/docs
```

and an OpenAPI schema endpoint at:

```text
http://127.0.0.1:8000/openapi.json
```

The exact available routes should always be verified against the running backend and its generated OpenAPI schema.

# 4. API Base URL

For local development:

```text
http://127.0.0.1:8000
```

The Flutter application obtains its backend base URL through the FireGuard configuration.

The Flutter application should not hard-code production infrastructure into feature-specific API calls.

A deployment environment can provide a different API base URL without changing the API contract itself.

# 5. Response Format

The API primarily communicates using JSON.

A successful response generally follows the structure defined by the corresponding FastAPI route and Pydantic response schema.

Example:

```json
{
  "id": 1,
  "status": "active"
}
```

Error responses are generated by FastAPI or by the application's validation and authentication logic.

Typical HTTP status categories include:

| Status | Meaning                            |
| ------ | ---------------------------------- |
| `200`  | Successful request                 |
| `201`  | Resource successfully created      |
| `400`  | Invalid request                    |
| `401`  | Authentication required or invalid |
| `403`  | Access denied                      |
| `404`  | Resource not found                 |
| `422`  | Request validation failed          |
| `500`  | Internal server error              |

The exact response body should be treated according to the active FastAPI route implementation.

# 6. Authentication

FireGuard uses backend authentication for application access and separate device authentication for capsule telemetry.

Authentication responsibilities are intentionally separated:

```text
Flutter Application
        │
        ▼
 Application Authentication
        │
        ▼
 FireGuard API

Physical Capsule
        │
        ▼
 Device Authentication
        │
        ▼
 Telemetry API
```

Device credentials are not intended to be exposed as ordinary application secrets.

Device authentication uses a generated device token, while the backend stores a protected representation rather than relying on plaintext device authentication secrets.

# 16. AI Fire Analysis

## POST `/api/ai/analyze-alert`

Runs FireGuard's fire-analysis pipeline against supplied telemetry and environmental information.

### Purpose

This endpoint provides the backend integration boundary for FireGuard's production AI analysis.

2. Environmental machine-learning evidence when valid environmental inputs are available.

# 19. Environmental Machine Learning

FireGuard's environmental ML component uses a trained and calibrated Random Forest model.

Production model package:

```text
fireguard_backend/ai/data/fireguard_calibrated_model.pkl
```

The model uses:

```text
era5_t2m_c
era5_d2m_c
era5_wind_speed_ms
era5_precip_m
```

The production predictor loads the model package lazily and uses the packaged feature metadata and calibration information.

Environmental ML is only applied when the required environmental inputs are actually available.

---

# 20. Interpretation of Environmental ML

The environmental ML estimate should not be interpreted as:

> "There is definitely a fire."

Instead, it represents an environmental fire-risk estimate based on the trained model and its data definition.

The project deliberately distinguishes:

```text
Environmental ML Risk
        ≠
Physical Fire Confirmation
```

Physical fire confirmation depends on the engineering sensor evidence and FireGuard's classification logic.

This distinction is important for responsible AI interpretation.

---

# 21. AI Confidence

FireGuard's alert confidence and environmental ML probability must not be treated as interchangeable values.

The production predictor distinguishes between:

* sensor agreement / engineering confidence
* environmental ML risk estimate

The environmental model's probability is not presented as an absolute physical probability of fire because the training labels are derived from satellite fire observations and controlled background observations rather than perfect physical ground truth.

This distinction is documented in:

```text
docs/ai.md
```

# 36. No-Hardware Development Policy

The FireGuard application can be developed and tested without physical hardware being permanently connected.

However, the project distinguishes clearly between:

```text
Software Testing
```

and:

```text
Real Physical Sensor Telemetry
```

Software tests must not be presented as evidence that physical hardware has successfully measured a real-world event.

Similarly, unavailable hardware measurements must not be fabricated and presented as real observations.

This distinction is important for scientific and engineering integrity.

# 37. Security Principles

The API follows several security principles:

* Authentication is handled by the backend.
* Device authentication is separated from application authentication.
* Device tokens are protected using hashing.
* Secrets should not be committed to the public repository.
* Environment-specific configuration should be supplied outside source control.
* The Flutter application should communicate with the API rather than directly accessing the database.
* Production deployments should use HTTPS.
* Production secrets should be managed through appropriate secret-management infrastructure.

The public repository must never contain:

```text
.env
private API keys
database credentials
production tokens
private certificates
private signing keys
```

---

# 38. Environment Configuration

Local environment configuration should be kept outside the public source repository.

A safe repository pattern is:

```text
.env
.env.example
```

The real `.env` file remains local and ignored by Git.

`.env.example` documents the configuration variables required by developers without containing real secrets.

# 39. CORS and Deployment

During local development, the backend may be configured for development clients.

For production deployment:

# 44. Failure Handling

The API should fail safely when required information is unavailable.

Examples include:

* Missing authentication.
* Invalid request data.
* Unknown capsule ID.
* Missing environmental data.
* Invalid telemetry.
* Database failures.
* External intelligence unavailable.

A temporary absence of environmental intelligence should not cause the backend to invent environmental values.

Similarly, failure to retrieve NASA FIRMS information should not automatically be interpreted as proof that no fire exists.

Versioning should only be introduced as an intentional compatibility strategy rather than changing routes unnecessarily during development.

# 54. Responsible AI and API Design

FireGuard's API deliberately separates:

```text
Observed Sensor Data
```

from:

```text
Environmental ML Estimates
```

and:

```text
Supporting Satellite Intelligence
```

This prevents the backend from presenting model estimates as direct physical measurements.

The system also avoids treating an environmental model output as definitive physical fire confirmation.

This distinction is fundamental to responsible engineering of a wildfire early-warning system.
